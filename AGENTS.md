# Working agreement for agents in this repo

This repo is Kunla. Work on it is tracked in Kunla itself (dogfooding).

- Build: `npm install`, then `npm test` (Vitest, runs the Worker against an in-memory SQLite D1 shim) and `npm run typecheck`.
- Run locally: `npm run dev` (Wrangler, local D1). Seed demo data with `node scripts/demo-seed.mjs http://localhost:8787`.
- Layout: `src/core.ts` holds all record-of-work logic as plain SQL; `src/kinds.ts` the kinds of work (guessing a task's kind, labelling deliverable links, what to hand in per kind); `src/mcp.ts` is the MCP server; `src/apps.ts` the interactive chat views (MCP Apps `ui://` resources for project_status and decision_inbox); `src/index.ts` the REST API; `src/oauth.ts` OAuth for chat connectors; `src/github.ts` GitHub webhooks; `src/githubapp.ts` the Kunla GitHub App (manifest flow, installs, installation tokens; app credentials are deployment-wide under `github_app`, and `github_installation:<id>` maps an installation to its workspace); `src/continuous.ts` continuous mode (limits, stop reasons, waking idle agents; daily cron in `scheduled`); `src/waits.ts` waiting on, assumptions, the bottleneck and the relations graph (KD-84); `public/` the static web app (no build step); `plugins/claude-code/` the Claude Code plugin and the `kunla` CLI; `src/extensions.ts` the plug-in points enterprise code registers into (policies, audit sinks, sign-in providers) and `src/licence.ts` the licence check (Community without a key); `src/transfer.ts` workspace export/import; `ee/` enterprise code under a separate license, which the core never imports.
- Migrations in `migrations/` only ever add tables or columns. Never rename or drop in the same release.
- Workspaces: `members`, `projects`, `tasks`, `events` and `webhook_deliveries` carry `space_id`. Every query and insert on them is limited to `c.space` (the workspace of the caller's token), and a migration that rebuilds one of these tables must keep `space_id`.
- Keep the core free of Cloudflare-only features (no Durable Objects, KV or queues) so it can run on SQLite or Postgres later.

## Kunla working agreement (for any agent using a Kunla board)
1. Before starting, get the task (`get_task` or `kunla show KEY`) and follow its brief, playbook and project rules.
2. Cite the task key in every output: `Task: KEY <link>` commit trailer, `key-slug` branch, `KEY: title` PR.
3. Record progress with `log_work` in one sentence. Work without a task still gets logged; Kunla creates the key.
4. Finish with `submit_for_review` and at least one deliverable link or `notes` with the outcome (all kinds of work count: Kunla's default kinds are code, writing, research, learning, discussion, outreach, design, operations, and each workspace or project can set its own list; see `kinds_here` and `how_to_finish` in `get_task`). Pass `session` (a link to your chat or agent session) when you claim, log or submit, so people can open the conversation from the task. Blocked? `update_task` with `blocked_question`. Can't go on until other work lands? `update_task` with `waiting_on` (a task key, a PR link, or a condition); if redoing later would be cheap, pass `assumption` and carry on instead.
5. Approved in Kunla means merge: when a person approves a task whose deliverable is your open PR, squash-merge it once checks pass (Kunla does it itself when it has a GitHub token). If checks fail or it conflicts, fix that first.
6. When your sponsor decides something about a task in your chat ("approve", "merge", "send it back", an answer to your question), call `record_decision` with their exact words and a link to the chat. It counts in Kunla as their decision, and they can undo it from the task. Never record a decision they didn't make. Agents can't mark work Done in a project that needs a person's review; send it for review instead.
7. One holder per task. Claim before working; if a task is already claimed, skip it (`next_task` gives you something else). If `heartbeat` or an update says the task is no longer yours (lease lapsed or a person took it over), stop. Stopping partway? `release_task` with a handoff note (what's done, what's left, where the branch is), optionally `to` a member. People can take over any claim from the task page.
